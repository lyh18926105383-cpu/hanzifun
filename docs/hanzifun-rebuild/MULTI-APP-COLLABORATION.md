# Codex、Cursor 与 Gemini 桌面端协作方案

更新：2026-11-02（Asia/Singapore）。状态：首轮实际协作已派发、回收并完成本地验收；见[三方交付](collaboration/seo-2026-11-02/DELIVERY.md)。下文初始试运行规则保留，末尾旧“未派发”为建立方案当时记录。

## 1. 已确认的环境与模型

- Owner 确认：Cursor 可以修改本地文件；Gemini 桌面端只能在云端工作，不能直接修改本地项目。
- Owner 确认：Cursor 当前可选 Grok 4.6、Grok 4.7、Composer 2.5；Gemini 可使用其各档模型，包括 Owner 称为最高端的 Argon。
- Codex 已通过桌面控制读取两个应用的界面；完整的任务派发、执行、回收链路仍待实跑。
- 上述模型名和可用范围按 Owner 说明记录；尚无本项目的模型对比结果。下述分工是试运行配置，不代表已经验证的性能排名、额度或计费结论。

## 2. 角色与模型选择

| 参与者 | 默认职责 | 交付物与责任边界 |
|---|---|---|
| Codex | 拆任务、检查真实代码、定义文件边界、实现集成部分、回收成果、测试与交接 | 本地集成代码、验证结果、TASKS/PROGRESS；负责最终验收 |
| Cursor · Composer 2.5 | 首轮本地实现的默认试用模型；承接接口与验收标准明确的模块 | 指定工作目录中的代码变更、修改清单、实际测试结果 |
| Cursor · Grok 4.7 / 4.6 | 可替换的本地执行模型；用于独立小任务试跑或同一问题的另一种解法 | 与 Composer 使用同样的文件边界和验收标准；切换前保存已有改动 |
| Gemini · Argon | 复杂方案设计、算法与数据规则推演、疑难问题根因分析、关键改动独立审查 | 带假设与接口定义的方案、边界用例、可定位的审查意见；必要时提供候选代码或补丁 |
| Gemini · 其他可选模型 | 需求归纳、资料整理、文案和格式转换等边界清晰的云端任务 | 结构化文本或数据草案；具体模型在派发时按界面和任务选择 |

复杂任务可以采用“Argon 提出方案 → Codex 对照仓库收敛接口 → Cursor 实现 → Codex 本地验收”的流程。Gemini 也可以在云端生成独立模块候选代码，由 Codex 审核后导入本地。云端测试只能证明其快照环境下的结果。

小改动由 Codex 或 Cursor 直接完成。仅在并行收益明确或需要独立分析时引入 Gemini，避免每个子任务都经过三方。

## 3. 拆分和并行规则

1. 从具体开发目标拆出可验证的交付物，逐项定义输入、输出、依赖、修改范围与验收命令。
2. 每个子任务只有一个实现负责人。需要共享接口时，先固定接口再让相关任务并行。
3. Cursor 与 Codex 优先使用从同一基线创建的独立 Git worktree 和分支，分支默认使用 `codex/` 前缀；用户指定目录时遵循指定目录。若共用目录，则按文件划定唯一写入者，交接后才能换人修改。
4. 共享路由、构建入口、全局样式、依赖清单、审核状态及交接总表默认由 Codex 整合；具体任务可以明确将其中的文件交给 Cursor。同一时段避免双方修改同一个文件。
5. Gemini 接收的是标有版本的材料快照。Codex 传递必要的需求、相关代码、接口和错误日志，并记录提交号；有未提交代码时同时记录所发文件的内容哈希。
6. UI 派发和结果读取由 Codex 依次操作；任务启动后，可在各应用独立运行时推进其他不依赖它们的工作。关键设计尚未确定的下游实现保持等待。

## 4. 一次任务的操作顺序

1. **准备**：阅读 PROGRESS、TASKS 与本次单个任务说明，检查实际目录、分支、未提交修改和现有验证方式。历史记录中的目录与发布版本仅作为线索，派发前核实。
2. **建立任务卡**：记录任务 ID、负责人、模型、基线、允许修改的文件、依赖、交付格式、验收方式与状态。实际任务材料可放在 `docs/hanzifun-rebuild/collaboration/<任务ID>/`；有真实任务时再创建。
3. **先确定规格**：复杂或不确定部分交给 Argon，Codex 用本地代码核对其前提并收敛成可执行规格。可独立实施的任务同步推进。
4. **派发实现**：在 Cursor 确认工作目录和选中的模型，提交任务卡及必要上下文。Gemini 云端任务收到自足的材料包，所有本地文件内容由 Codex 提供，不能要求它直接读取本机路径。
5. **跟踪**：Codex 读取执行状态、处理有具体依据的澄清，并记录卡点。界面显示已发送才记为已派发；模型声称完成后先记为已回收。
6. **回收**：Cursor 提交文件清单、diff 与测试记录。Gemini 返回结构化结论、证据和适用基线；候选代码或补丁由 Codex 对照最新本地代码审查并落盘。引用资料保留来源，无法确认的前提标注待核验。
7. **验收**：检查越界修改、遗漏与版本漂移，审查后合并；按当前任务要求执行必要测试、构建和浏览器检查。Gemini 审查意见逐条记录采纳或不采纳的理由。材料变化影响到的结论需要重新核对。
8. **收口**：以本地验收结果判定任务完成，更新 TASKS 与 PROGRESS，记录文件、遗留问题及下一步。发布依照具体任务已有授权和项目流程处理。

状态依次为：待派发 → 已派发 → 执行中 → 已回收 → 已验收。需要前置输入时记“阻塞：具体原因”。AI 回复“完成”和云端测试通过都不能直接跳到本地“已验收”。

## 6. 首轮试跑与模型调整

- 从下一项真实开发需求中选一个低耦合、容易验收的小子任务：Composer 2.5 负责本地实现，Argon 负责一个明确的设计问题或独立审查，Codex 负责集成验收。
- 记录首次验收是否通过、返工次数、总完成时间、上下文传递次数及界面可观察的用量。材料不足、接口不清、操作失败与模型实现错误分别记录。
- 若 Composer 的交付不满足要求，先定位原因；确需更换模型时，在保留现有成果后使用 Grok 4.7 或 4.6，沿用相同验收标准。首轮不为排名重复实施整项功能。
- Argon 的结论同样由证据、可实施性和本地验证评价；角色可以随实际表现调整，不仅按型号名称分配难度。
- 若外部应用不可用、达到使用限制或无法读回结果，记录真实状态，将必要工作收回 Codex 或转交另一可用执行方；由应用中已有登录和可用模型完成派发，不自动改用付费 API。

## 7. 项目规则与当前状态

本方案约定协作方式，具体开发范围继续遵循 Owner 指令与项目约束。保持现有轻量本地架构，未明确启动的账号、云同步、Billing 仍不引入。涉及故事课时，制作前须完整阅读根目录 STORY_COURSE_PRODUCTION_WORKFLOW.md，并执行其规定的人工确认及验证步骤。

本轮仅建立文档与交接入口；未派发实际子任务、切换外部应用模型、创建工作树、执行产品测试或部署。下一步由具体开发需求触发首轮试跑。
